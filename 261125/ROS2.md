# 2026-11-25 — 자연어를 하위 작업으로 바꾸기

[12강 교안](<../ref/ROS2/12강. 자연어를 하위 작업으로 바꾸기.pptx.pdf>) 1~23쪽. 자연어 지시를 작업 명세로 바꾸고, 선행 관계·현재 상태·장비 사용을 따로 검사하는 내용을 정리했다.

## 지시를 완료 조건으로 바꾸기

“A에서 상자를 가져와 B에 놓고 충전해”에는 대상, 목적지, 순서와 완료 조건이 들어 있다.

- 빨간 상자가 두 개라면 어느 상자인지 되묻고, 답을 현재 관측과 대조해 물체 ID를 정한다.
- 놓기 완료는 상자가 B에 있고 손이 비어 있는 상태다.
- 교안에서 충전 완료 기준은 충전기에 도착하는 것이 아니라 연결 후 **충전 중 신호가 켜지는 것**이다. 완충까지 기다린다는 뜻은 아니다.
- 상자를 놓은 뒤 충전해야 하므로 최종 상태뿐 아니라 사건의 순서도 확인한다.

## 스키마와 작업 ID에서 헷갈린 부분

스키마는 명령에 필요한 필드·자료형·허용값을 정하는 규칙이다. 아래 JSON은 스키마 자체가 아니라 그 규칙에 맞춰 작성한 작업 데이터다.

```json
{
  "id": "t2",
  "op": "pick",
  "object_id": "box_02",
  "after": ["t1"]
}
```

뜻은 **t1이 성공적으로 완료된 뒤 box_02를 집는 t2를 실행한다**는 것이다. t1·t2는 작업 ID이고 box_02는 물체 ID다. 물체를 옮기면 t1으로 바뀌는 것이 아니다. t1이 어떤 동작인지는 계획에서 해당 ID의 작업을 찾아야 한다.

필드 형식이 맞더라도 실행 가능한 계획이라는 보장은 없다. 작업 ID 중복, 허용된 동작인지, 관측에 있는 물체인지, `after`의 ID가 실제 계획에 등록되어 있는지 별도로 확인한다.

## 작업은 나열보다 의존 관계로 표현

```text
A로 이동 → 집기 → B로 이동 ─┐
                           ├→ 놓기 → 충전기로 이동 → 충전 시작
B 공간 조회 ────────────────┘
```

놓기는 B 도착과 공간 조회가 모두 끝나야 가능하다. `after`에는 직접 선행하는 작업을 적으면 된다. 단, 이전에 공간이 비었다고 확인했어도 놓기 직전에 그 관측이 유효한지 다시 확인해야 한다.

의존 관계에 순환이 생기면 시작할 수 없다. 또 선행 관계가 없는 두 작업이라도 차체나 팔 하나를 같이 쓰면 동시에 실행할 수 없다. **의존 관계와 자원 충돌은 별도 검사**다. 교안처럼 고정 카메라가 독립적이라면 B 공간 조회와 차체 이동은 겹칠 수 있다.

위상 정렬은 선행 관계를 지키는 순서를 구한다. 가능한 순서는 하나가 아닐 수 있으며, Python의 `TopologicalSorter`는 선행 목록에만 등장하는 ID도 노드로 받아들인다. 따라서 `t1`을 `t9`로 잘못 적은 문제는 정렬 전에 등록 ID 검사로 잡아야 한다.

## 명령 전송과 작업 성공은 다르다

그리퍼를 닫았어도 상자가 작업대에 남아 있으면 집기 실패다. 예상 효과를 성공으로 기록하지 말고 파지 결과를 확인한 뒤 운반으로 넘어간다. 로봇이 B에 도착한 것과 상자를 B에 내려놓은 것도 다른 상태다.

공간 상태는 `true / false / unknown`으로 구분한다. 카메라가 가려져 알 수 없는 상태를 빈 공간이나 점유 상태로 단정하지 않는다.

집기에 실패했지만 A 도착 상태가 여전히 유효하다면, 처음부터 다시 이동할 필요 없이 상자 자세를 재관측하고 집기부터 고친다. B가 막혀 있어도 목적지를 C로 임의 변경하지 않고 대기하거나 사용자에게 확인한다.

## 계획과 실행 가능성 연결

상태 공간 탐색은 현재 가능한 행동을 찾고, 작업 분해는 큰 작업을 하위 작업으로 나눈 뒤 조건을 확인한다. 손에 다른 상자가 들려 있다면 먼저 내려놓을 수 있는지부터 검토해야 한다.

교안의 SayCan은 지시와의 관련성과 현재 실행 가능성을 함께 고려하는 사례다. Inner Monologue는 실행 피드백으로 다음 행동을 수정하는 사례다. 계획 문장을 만드는 데서 끝내지 않고, **실제 관측을 다음 작업의 조건으로 넘기는 것**이 핵심이다.
