  - 같은 PPO라도 구현·정규화·하이퍼파라미터·환경이 다르면 결과가 다름
- "RCL-RL"처럼 헷갈리기 쉬운데 정확히는 RSL-RL

## 로봇 파일이 학습 환경이 되기까지
- 로봇 자산: 모양·관절·질량·관성
- 장면: 바닥·물체·접촉·중력을 더함
- 환경: 관측으로 무엇을 주고, 어떤 행동을 허용하고, 어떤 점수를 줄지 정의
- 학습기: 환경에서 받은 경험으로 정책 가중치를 갱신
- 한 스텝: 관측 $o_t$ → 정책이 행동 $a_t$ → 구동기 → 물리 계산 → $o_{t+1}$, 보상 $r_t$, 종료 플래그
  - 평가 때도 순서는 같고 가중치만 갱신하지 않음

| 용어 | 뜻 | 예 |
|---|---|---|
| State | 시뮬레이터 안의 전체 값 | 위치·속도·접촉·물성 |
| Observation | 그중 정책에 실제로 넘기는 값 | 몸체 속도, 관절각, 목표 |
| Transition | 상호작용 한 번의 기록 | $(o_t, a_t, r_t, o_{t+1})$ |
| Rollout | transition을 모은 묶음 | 환경당 수백 스텝 |

- 정책은 화면 속 로봇을 "보지" 않음. 카메라를 안 넣었다면 배열 숫자만 봄
  - 목표가 바뀌는 과제면 **목표나 목표 오차를 관측에 넣어야** 같은 자세에서 어느 쪽으로 갈지 정할 수 있음

## 신경망, Actor, Critic
- MLP: 숫자 벡터를 여러 층의 가중치 + 비선형 함수로 변환하는 신경망
  - 입력 크기 = 관측 개수, 출력 크기 = 행동 설계로 정해짐 (관절 8개라고 관측이 8개인 건 아님)
- Actor: 행동을 고르는 정책망 $\pi_\theta$
  - 연속 제어 학습 중에는 행동 **분포에서 표본**을 뽑아 탐색
- Critic: 지금 관측에서 앞으로 받을 수익을 예측하는 가치망 $V(o_t)$
  - 모터에 명령을 내리지 않음. 학습 신호(advantage) 계산에만 씀
  - 구현에 따라 Actor와 층을 공유하기도, 분리하기도 함 ([261020](../261020/ROS2.md#ppo-설정-rsl_rl-onpolicyrunner)의 rsl_rl은 actor·critic 각각 MLP)

| 용어 | 뜻 | 코드에서 |
|---|---|---|
| Parameter | 학습으로 바뀌는 가중치 | 정책 모델 안 |
| Hyperparameter | 사람이 정하는 학습 설정 | `learning_rate`, `batch_size` |
| Inference | 현재 가중치로 행동 계산 | `model.predict()` |
| Gradient | 가중치를 바꿀 때 손실이 변하는 정도 | 라이브러리의 역전파 |
| Optimizer | gradient로 가중치를 갱신하는 방법 | PPO 내부 |
| Checkpoint | 가중치·학습 상태 저장 파일 | `policy.zip` |

## 보상, 수익, 가치, Advantage
- 보상 $r_t$: 한 스텝의 점수
- 수익 $G_t$: 지금부터 받을 보상의 할인 합

$$
G_t = \sum_{k=0}^{T-t-1} \gamma^k \, r_{t+k} = r_t + \gamma r_{t+1} + \gamma^2 r_{t+2} + \cdots
$$

- 할인율 $\gamma$가 1에 가까울수록 먼 미래까지 크게 반영
  - **제어 주기를 바꾸면 같은 $\gamma$라도 실제 시간으로 보는 범위가 바뀜**
  - 보충: 대략 $1/(1-\gamma)$ 스텝 앞까지 본다고 생각함. $\gamma=0.99$면 약 100스텝 → 50Hz면 약 2s, 100Hz면 약 1s
- 가치 $V(o_t)$: $G_t$의 예측값 (Critic의 출력)
- Advantage $A_t$: 그 행동이 **예상보다 얼마나 좋았나**. 직관적으로 $A_t \approx G_t - V(o_t)$
- 예 (교안 수치): 보상 1, 2, 3, $\gamma = 0.9$

$$
G_t = 1 + 0.9 \times 2 + 0.81 \times 3 = 5.23, \qquad V(o_t) = 4 \;\Rightarrow\; A_t \approx 1.23
$$

  - $A_t > 0$ → 그 행동의 확률을 높이고, $A_t < 0$ → 낮추는 방향으로 갱신
- 실제 PPO 구현은 $G - V$ 대신 **GAE**(Generalized Advantage Estimation)를 씀: 여러 시간 범위의 추정을 섞고 `gae_lambda`로 섞는 정도를 조절
- 보충 (GAE 식): 한 스텝 TD 오차를 할인해서 더함

$$
\delta_t = r_t + \gamma V(o_{t+1}) - V(o_t), \qquad \hat{A}_t = \sum_{l=0}^{\infty} (\gamma\lambda)^l \, \delta_{t+l}
$$

  - $\lambda = 0$이면 $\hat{A}_t = \delta_t$ (편향 크고 분산 작음), $\lambda = 1$이면 $G_t - V(o_t)$ (편향 작고 분산 큼)
  - $\delta_t$의 $r_t + \gamma V(o_{t+1})$은 벨만 식 $V(o_t) = \mathbb{E}[r_t + \gamma V(o_{t+1})]$의 한 표본 → 예측이 정확하면 $\delta$의 평균이 0

## PPO 갱신을 더 자세히
- 식 자체는 [261019 PPO](../261019/ROS2.md#ppo)에 정리. 교안 기호로는 확률비를 $\rho_t$로 씀

$$
\rho_t(\theta) = \frac{\pi_\theta(a_t \mid o_t)}{\pi_{\theta_\text{old}}(a_t \mid o_t)}, \qquad
L(\theta) = \mathbb{E}_t\Big[\min\big(\rho_t A_t,\ \text{clip}(\rho_t, 1-\epsilon, 1+\epsilon)\, A_t\big)\Big]
$$

- $\theta_\text{old}$: 자료를 **모을 때**의 정책. 갱신 중인 정책과 비교함
- Advantage 부호별로 어디서 목적식이 평평해지나
  - $A_t > 0$: $\rho_t > 1+\epsilon$부터 더 올려도 이득 없음 → 좋은 행동을 과하게 강화하지 않음
  - $A_t < 0$: $\rho_t < 1-\epsilon$부터 더 내려도 이득 없음 → 나쁜 행동 확률을 한 번에 너무 깎지 않음
- 오해하기 쉬운 점
  - $\epsilon = 0.2$는 목적식 계산에서 [0.8, 1.2] 구간을 쓴다는 뜻. **모터 출력을 20%로 제한하는 게 아님**
  - 실제 $\rho_t$가 항상 그 구간 안에 갇히는 것도 아님. "개선 유인"을 잘라낼 뿐
  - 모터 한계는 구동기 설정과 행동 스케일에서 정함
- 실제 손실은 정책 손실 + 가치 손실 + 엔트로피 항

| 로그 지표 | 뜻 | 볼 때 |
|---|---|---|
| entropy | 행동 분포가 퍼진 정도 | 탐색이 충분한지 |
| value loss | 가치 예측 오차 | Critic이 수익을 따라가는지 |
| approx_kl | 갱신 전후 정책 분포 변화량 | 한 번에 너무 바뀌는지 |

- 이 지표 중 어느 것도 **과제 성공을 판정하지 않음** → 평가는 따로

## 첫 목표 고르기
- 첫 목표는 **수치로 검사할 수 있는 동작 하나**. 미로 주행 전체를 거대한 보상 하나로 만들지 않음

| 로봇 | 시작 과제 | 이후 확장 |
|---|---|---|
| 바퀴 로봇 | 구동 관절 속도 추종 또는 몸체 전진 속도 | 방향 전환, 목표 지점 이동 |
| 로봇팔 | 선택 관절의 자세·속도 추종 | 끝단 목표 도달, 물체 조작 |
| 다족 | 안정된 초기 자세 유지 | 균형, 보행 |
| 복합 | 구동부 하나의 동작 | 여러 기능 순차 수행 |

- 제공 환경 `my_robot_env.py`는 "선택 관절의 속도 추종"이 공통 출발점
  - **관절 속도가 맞는 것 ≠ 몸체가 전진하는 것**. 바퀴가 공중에서 돌아도 점수가 높을 수 있음
  - 주행 과제면 몸체 속도·접촉·전복 조건을 관측과 보상에 추가
- Gymnasium 공식 MuJoCo 예제에서 볼 점
  - Ant(다족): 관절 토크와 몸체 이동·건강 상태(넘어지지 않음)를 같이 봄
  - Reacher(팔): 관절이 움직이는 것과 **끝단 오차가 줄어드는 것**은 다름
  - Humanoid: 자유도가 많고 몸체 높이·넘어짐 조건 설계가 핵심
  - 그림의 관절 수를 내 로봇에 복사하지 않음

## MuJoCo 장면 준비
- 본 실습은 내 로봇의 MJCF 장면. URDF를 변환한 XML은 **시작점**일 뿐
  - 구동기, 바닥, 초기 자세, (필요하면) 자유 베이스가 있는지 확인
  - 메시 파일 전체와 상대 경로를 보존
- 구동기
  - `nu` = actuator 개수. 관절이 있어도 actuator가 없으면 `data.ctrl`로 못 움직임
  - joint·actuator 이름은 **실제 모델에서 조회**해서 설정에 적음
  - `motor`: 보통 힘·토크 입력 / `velocity`: 속도 목표 → 제어 종류에 따라 `ctrl_scale`의 단위가 바뀜

| 관절 | `ctrlrange` (velocity 구동기) | `forcerange` |
|---|---|---|
| 회전 (hinge) | rad/s | N·m |
| 직선 (slide) | m/s | N |

- 고정 베이스/자유 베이스는 동작 목표로 정하고, 변환 후에도 의도대로인지 확인
- MuJoCo 모델 요소

| 요소 | 뜻 |
|---|---|
| body | 강체와 그 좌표계 |
| geom | 시각·충돌 형상 |
| site | 목표·센서의 기준점 (충돌 없음) |

- 접촉
  - MuJoCo는 작은 침투를 허용하는 soft contact. `solimp`(임피던스 곡선)·`solref`가 힘과 침투 깊이의 관계를 바꿈
  - 처음엔 기본값 유지, 접촉 문제가 생기면 그때 공식 문서와 같이 봄
  - 보상 튜닝 전에 비정상 접촉, 관성, 시간 간격부터 확인
  - 접촉 좌표계: 법선과 접선(마찰) 방향을 구분. 마찰은 타원형(elliptic) 또는 각뿔 근사(pyramidal)
  - 접촉력(접촉 좌표계)과 몸체 좌표계 값을 섞어 보상을 계산하지 않음
- 지연: MuJoCo 구동기 지연 버퍼가 과거 입력을 저장해 늦게 적용 (사이 값은 이전 값 유지 또는 선형 보간)
  - 지연이 있는 로봇이면 "지금 행동이 바로 반영된다"고 가정하면 안 됨 → [261021 행동 지연 랜덤화](../261021/ROS2.md#시스템-행동-지연과-샘플-주기)와 연결
- 연결 순서 (교안 흐름도)
  1. URDF/MJCF·메시 경로와 단위 확인
  2. 관절·구동기 매핑 (이름·범위·방향)
  3. 0 입력, 작은 입력을 넣고 렌더링으로 확인
  4. 물리가 불안정하면 질량·관성·충돌·축·제어 범위를 고치고 2부터 다시
  5. 안정하면 환경 함수 작성 (관측 → 보상 → 종료)
  - 불안정한 모델을 PPO 설정으로 해결하려 하지 않음. 모델 단계로 돌아감
- 화면이 뜨는 것 ≠ 학습 준비 완료

## 관측·행동의 차원과 좌표계
- 제어 관절 $J$개일 때 기본 환경
  - 관측 $3J$: 관절 위치 $J$ + 정규화 속도 $J$ + 정규화 목표 속도 $J$
  - 행동 $J$
  - 위치는 원래 rad·m 그대로라 **내 로봇 범위에 맞는 위치 정규화**를 추가해야 함
- 병렬 환경 $N$개로 묶으면 shape

| 배열 | shape |
|---|---|
| 관측 | $(N, 3J)$ |
| 행동 | $(N, J)$ |
| 보상 | $(N,)$ |

- 보상은 $J$축 오차를 평균 내서 환경별 하나. **$N$축까지 평균 내면 안 됨** (환경마다 따로 점수가 있어야 함)
- `qpos`, `qvel` 주소는 따로 조회
  - 보충: free joint는 `qpos` 7개(위치 3 + 쿼터니언 4), `qvel` 6개라 두 배열 길이가 다름
  - 쿼터니언을 일반 관절 값 하나처럼 다루면 안 됨
- 좌표계
  - 세계 좌표 속도와 몸체 좌표 목표를 그대로 빼면 틀림 → 같은 좌표계로 변환 후 비교
  - yaw 오차는 ±π 경계에서 튐 → 각도 차이를 감싸거나 $(\sin\psi, \cos\psi)$로 표현
  - 보충: 감싸기는 $\Delta\psi = \operatorname{atan2}\big(\sin(\psi_\text{goal}-\psi),\ \cos(\psi_\text{goal}-\psi)\big)$

## 환경 함수 설계 (Gymnasium 계약)
- 함수마다 입력·출력·단위·상태 변경·잘못된 입력 처리를 먼저 적고 구현
- 보상 함수가 물리를 진행하거나 초기화하면 안 됨 (계산만)

| 함수 | 입력 → 출력 | 내용 |
|---|---|---|
| `__init__` | 설정 → 환경 | 모델 로드, 이름·주소 조회, 공간 선언 |
| `_get_obs` | 물리 상태 → float32 배열 | 관측 순서와 스케일 |
| `reset` | seed → `obs, info` | 초기 자세, 목표, 카운터 |
| `step` | action → 결과 5개 | 구동, 물리 진행, 점수, 종료 |
| `_reward` | action → 보상·오차 | 목표 항과 비용 항 |

- `step`의 반환: `observation, reward, terminated, truncated, info`

| 플래그 | 뜻 | 예 |
|---|---|---|
| terminated | 과제 자체가 끝남 | 전복, 작업 구역 이탈, (설계에 따라) 성공 |
| truncated | 외부 사정으로 중단 | 시간 한도 |

- 제공 기본 환경은 `terminated`가 항상 False → **내 로봇의 실패 조건을 직접 구현**해야 함
- `info`에는 점수 말고 실제 오차·실패 원인 같은 진단값
- 두 경우 모두 최종 관측을 보존한 뒤 reset
- 보충: 둘을 구분하는 이유는 가치 계산. terminated면 그 뒤 수익이 0이고, truncated면 원래 계속될 상태라 $\gamma V(o_{t+1})$로 이어 붙여야 함 (처리 방식은 라이브러리 규약을 따름)
- 시간 (교안 예시값)

| 설정 | 값 | 의미 |
|---|---|---|
| physics_dt | 0.002s | 물리 500Hz |
| decimation | 10 | 정책 명령 하나를 물리 10스텝 동안 유지 |
| 정책 주기 | 0.002 × 10 = 0.02s | 50Hz |
| max_steps | 250 | 250 × 0.02 = 5s 에피소드 |

- seed: 초기 난수 조건을 재현하는 값
- decimation 개념은 [261021 병렬 환경과 주기](../261021/ROS2.md#병렬-환경과-주기)와 같음

## 보상 함수
- 기본 예제: 관절 속도 오차를 관절별 `velocity_scale`로 나눠 정규화한 뒤

$$
e = \frac{\dot q - \dot q_\text{goal}}{s_v}, \qquad
r = \underbrace{\exp\!\big(-\operatorname{mean}(e^2)\big)}_{\text{추종}} - \underbrace{0.01 \cdot \operatorname{mean}(a^2)}_{\text{행동 비용}}
$$

- 단위·범위가 다른 값을 한 점수에 섞기 전에 정규화
- 과제별로 바꿀 것
  - 주행: 몸체 전진·횡방향 속도와 yaw rate 오차, 전복·충돌은 따로 처리
  - 팔 끝단: 위치 오차를 m로, 관절 한계·자세·접촉 조건 추가
- 함정
  - 비용 항이 너무 크면 **가만히 있는 편이 유리**해짐
  - 성공하면 바로 종료하면서 매 스텝 양의 보상을 주면 **일부러 늦게 끝내는** 전략이 유리 → 종료·시간 비용·성공 보너스를 같이 설계
- 손계산 검사: 잘하는 상태 / 실패 상태 / 가만히 있는 상태의 점수 순서가 맞는지
  - 내 계산 (교안 설정 예시값 `ctrl_scale` 2, `velocity_scale` 2, 목표 +1 rad/s, 관절 1개)

| 상태 | 속도 | 행동 $a$ | $e$ | 추종 | 비용 | 보상 |
|---|---|---|---|---|---|---|
| 정확히 추종 | +1 | 0.5 | 0 | 1.000 | 0.0025 | 0.998 |
| 가만히 있음 | 0 | 0 | −0.5 | 0.779 | 0 | 0.779 |
| 반대로 회전 | −1 | −0.5 | −1 | 0.368 | 0.0025 | 0.365 |

  - 순서는 맞음. 다만 가만히 있어도 0.78을 받아 추종과 차이가 0.22뿐 → exp 형태는 오차가 작을 때 기울기가 완만함. 학습 신호가 약하면 이 차이를 키울지 검토할 것

## 로봇 설정 파일 (`robot_config.json`)
- 템플릿을 복사해 내 모델 경로와 관절을 채움. `model` 경로는 `assets/` 기준
- 제어할 관절마다 `drives` 항목 하나

| 키 | 뜻 |
|---|---|
| `ctrl_scale` | 행동 ±1에 대응하는 구동 입력 크기 (velocity 구동기에서 2면 ±2 rad/s 목표) |
| `velocity_scale` | 관측·오차를 나누는 기준. `ctrl_scale`과 같을 필요 없음 |

| `decimation`, `max_steps` | 위 시간 표의 값 |

- reset은 모델 기본 자세를 씀 → 충돌 없는 기본 자세부터 설정
- 회전 범위가 제한된 관절에 오래 일정 속도를 명령하지 말고 짧은 목표·자세 추종으로 바꿈

## PPO 학습 구조와 설정 (SB3)
| 설정 | 의미 | 교안 기본값 |
|---|---|---|
| `learning_rate` | 한 번 갱신의 보폭 | 0.0003 |
| `n_steps` | 환경당 수집 길이 | 1024 |
| `batch_size` | gradient 한 번의 표본 수 | 256 |
| `n_epochs` | 같은 rollout을 반복 학습하는 횟수 | 5 |
| `total_timesteps` | 전체 transition 목표 | 100000 |
| `seed` | 학습 난수 초기 조건 | 7 |

- 환경 1개 기준: 1024개 수집 → 256개씩 4묶음 → 5 epoch → **4 × 5 = 20번 optimizer 갱신** → 갱신된 정책으로 새로 수집
  - 오래된 rollout은 재사용하지 않음 (PPO는 수집한 정책 기준으로 확률비를 계산하므로)
- rollout 단위로 끝나서 실제 수집량이 요청보다 클 수 있음
  - 내 계산: 100000 / 1024 = 97.7 → 98번 수집 = 100,352 transition, smoke 2048은 정확히 2번
- 단위 혼동 주의
  - epoch: 같은 수집 자료를 한 바퀴 학습. **에피소드 수가 아님**
  - iteration: 라이브러리마다 정의가 다름 (보통 수집+갱신 한 묶음) → 로그 정의 확인
  - 100000스텝, 300 iteration 같은 숫자는 성공 보증이 아님 ([261020](../261020/ROS2.md#학습-결과)에서 300회 돌려도 균형을 못 배운 사례)
- [261020](../261020/ROS2.md#ppo-설정-rsl_rl-onpolicyrunner)의 rsl_rl 설정과 대응
  - SB3 `n_steps` ↔ rsl_rl 환경당 수집 스텝(그때 16), `n_epochs` ↔ 5 epoch, `batch_size` ↔ 미니배치 개수(그때 4)로 지정하는 방식 차이

## 평가와 문제 해결
- 학습 수익 그래프는 최적화가 진행 중이라는 **단서**일 뿐
- 별도 평가에서 볼 것: 성공률, 최종 오차, 전복·충돌, 구동 한계 초과
  - 학습에 안 쓴 초기 조건·목표로
  - 기준선과 비교: 무동작, 무작위, 기존 제어기
  - 평균뿐 아니라 실패 사례도 남김
  - `deterministic=True` (분포의 평균 행동), 가중치 갱신 없음
- 찾아야 할 편법: 몸체는 안 가고 바퀴만 도는 것, 팔이 목표 근처에서 진동, 한 초기 자세에만 맞는 정책
- 학습이 안 될 때 점검 순서 (교안 흐름도)

| 순서 | 질문 | 아니면 |
|---|---|---|
| 1 | 수동 입력에 정상 반응? | 구동기 이름·방향, ctrl 범위, 충돌 검사 |
| 2 | 관측·보상이 모두 유한값? | NaN 발생 시점 추적, 단위·나눗셈·물리 검사 |
| 3 | 목표 행동의 보상이 더 큰가? | 수치 사례로 보상 수정, 종료·리셋 조건 검사 |
| 4 | 위 셋 통과 | 관측에 목표 판단 정보가 있는지, 행동 범위, 평가가 학습과 같은 단위·규약인지 |

  - PPO 하이퍼파라미터 조정은 **그다음**. 한 번에 한 항목만 바꿈
- 저장 정책 평가 순서
  1. 정책과 설정(모델·버전) 기록
  2. 관측 순서·행동 스케일·정규화 통계가 학습 때와 같은지 확인 (다르면 학습 때 설정과 통계를 복원)
  3. 새 seed·초기 조건에서 갱신 없이 평가
  4. 에피소드별 성공률·오차·실패 수 기록
  5. 같은 평가 조건으로 이전 정책과 비교
- 주의
  - 파일이 로드된다고 호환되는 건 아님
  - `VecNormalize` 같은 관측 정규화를 쓰면 그 통계도 저장·복원
  - 관측을 바꾸면 입력 차원이 달라져 기존 모델을 못 읽을 수 있음
  - 정규화·좌표계·구동 스케일을 바꾸면 같은 행동 숫자가 다른 물리 명령이 됨

## Isaac Lab + RSL-RL 확장
- 책임 분리: **Isaac Lab = 환경**(물리 상태·관측·보상·종료), **RSL-RL = 학습**
  - Runner: 수집·학습 반복 관리 / 정책·가치 모델: 행동과 가치 계산 / rollout storage: 경험 저장 / PPO 객체: advantage·손실·갱신
  - 과제 함수에 역전파 코드를 넣지 않음. 클래스 이름은 버전마다 다를 수 있음
- Direct 방식 함수와 역할 (Manager 방식과의 비교는 [261021](../261021/ROS2.md#manager-방식과-direct-방식))

| 함수 | 연결할 설계 | 결과 |
|---|---|---|
| `_pre_physics_step` | 행동 스케일·제한 | 배치 명령 준비 |
| `_apply_action` | 구동기에 목표 전달 | 물리 입력 |
| `_get_observations` | 관측 배열 구성 | 정책 관측 |
| `_get_rewards` | 환경별 보상 | $(N,)$ |
| `_get_dones` | 실패, 시간 제한 | bool 배열 2개 (terminated, truncated) |
| `_reset_idx` | 끝난 환경만 초기화 | `env_ids`의 상태 갱신 |

- Direct와 Manager의 차이는 **코드 조직 방식**이고 물리 엔진 선택과는 별개
- Lab 3.0 물리 선택
  - 기본은 Newton 백엔드. `--extra isaacsim`은 구성 요소 설치, `physics=isaacsim_physx`는 물리 선택
  - `--viz none`은 화면만 끔. GPU 요구는 그대로
- 흐름
  - `uv run isaaclab --new` → External project, Direct single-agent, rsl_rl, PPO 선택
  - 생성 예제가 돌아가는지 먼저 확인한 뒤 USD·로봇 설정·관측·보상·초기화·종료를 교체
  - 태스크 이름을 확인한 뒤 `train`(예: 환경 64개, 10 iteration, 화면 없음) → `play`(최근 체크포인트, 환경 16개, 화면)
  - [261020](../261020/ROS2.md#6-실습-4--isaac-lab-cartpole-ppo)에서는 수업 고정 커밋에 `list_envs` 하위 명령이 없어 `scripts/environments/list_envs.py`로 대체했음 → 같은 문제가 나면 그 방법으로
  - 2.x API를 섞지 않고 Lab 3.0 공식 문서를 따름
- MuJoCo → Isaac Lab 이전 (sim-to-sim)
  - 옮기는 건 **설계 의도**. 상태 API·좌표계·접촉·시간 간격은 다시 검사
  - SB3 `policy.zip`을 RSL-RL이 바로 읽는다고 가정하지 않음 → Isaac에서 따로 학습·평가
  - 같은 태스크라도 엔진의 물리·구동·접촉 차이로 성능이 달라짐

## 제출물과 완료 기준
- 필수: 로봇 장면과 참조 파일, 관측·행동·보상 설계표, 수정한 환경 함수, 실행 설정·명령, `policy.zip`, 새 조건의 평가 기록, 동작 캡처, 실패 분석
- 먼저 만족할 것: API 통과, 상태가 유한값, 의도한 행동 방향, 로봇별 실패 조건 구현
- 성공 기준은 과제의 목표 오차·유지 시간·시험 횟수와 함께 **미리** 정함 (모든 로봇에 같은 기준을 쓰지 않음)
- 학습이 실패해도 수익과 실제 과제 지표를 비교해 원인을 설명하면 기록이 됨

## 용어 정리
| 용어 | 뜻 |
|---|---|
| Rollout | 현재 정책으로 모은 경험 묶음 |
| Minibatch | 한 번의 gradient 갱신에 쓰는 작은 묶음 |
| Epoch | 같은 rollout을 한 바퀴 학습 |
| Return $G_t$ | 미래 보상의 할인 합 |
| Value $V(o_t)$ | 수익의 예측 |
| Advantage $A_t$ | 예상보다 좋았던 정도 |
| GAE | 여러 시간 범위의 advantage 추정을 섞는 방법 ($\lambda$로 조절) |
| $\epsilon$ (clip) | 확률비 개선 유인을 자르는 폭 |
| Entropy | 행동 분포의 퍼짐, 탐색 정도 |

## 확인 문제 (내 답)
- 교안의 영상 시청용 질문에 답함
1. 관측·행동·보상은 어떻게 반복되나?
   - 환경이 관측을 주면 정책이 행동을 내고, 환경이 물리를 진행해 다음 관측·보상·종료 여부를 돌려줌. 종료되면 reset으로 새 에피소드 시작. Gymnasium에서는 `reset`의 반환과 `step`의 반환 5개가 이 화살표에 대응
2. 병렬 환경은 수집 경험을 어떻게 늘리나?
   - 같은 정책으로 $N$개 환경을 한 번에 진행하므로 한 번의 수집에 환경당 스텝 × $N$개 transition이 모임. 환경마다 상태·시작점이 달라 경험도 다양해짐 (대신 메모리 증가)
3. 쉬운 지형에서 어려운 지형으로 바꾸는 이유는?
   - 처음부터 어려우면 거의 실패만 해서 보상 신호가 없음. 쉬운 조건에서 기본 동작을 익힌 뒤 난도를 올리는 커리큘럼 ([261021](../261021/ROS2.md#커리큘럼과-adr))
4. 시뮬레이터와 학습 프레임워크의 역할은?
   - Isaac Sim(시뮬레이터)은 장면·물리·센서를 계산, Isaac Lab(프레임워크)은 그걸 관측·행동·보상·종료가 있는 태스크로 묶어 병렬 환경으로 학습기(RSL-RL)에 연결
5. (교안 내용으로 내가 낸 문제) $\epsilon = 0.2$면 모터 출력이 20%로 제한되나?
   - 아님. 목적식에서 확률비의 개선 유인을 [0.8, 1.2]에서 자를 뿐이고 모터 한계는 구동기와 행동 스케일에서 정함
