## 1. SLAM과 Navigation의 역할

SLAM은 센서와 이동 정보를 이용해 지도와 로봇의 위치·방향을 함께 추정한다. Navigation은 현재 위치에서 목표까지 경로를 계획하고, 경로를 따라 움직일 속도 명령을 계산한다. 저장 지도를 사용하는 주행에서는 AMCL이 위치를 추정하고 Nav2가 계획·제어를 수행한다.

경로(Path)는 공간에서 지나갈 위치·방향의 열이다. 궤적(Trajectory)은 시간에 따른 상태와 속도까지 포함한다. 경로가 생성되었다고 로봇이 그 경로를 실제로 추종할 수 있다는 뜻은 아니다.

Waffle은 차동 구동이므로 전후진 선속도와 회전 각속도를 사용하며 횡이동은 하지 못한다. 명령을 보내는 노드와 받는 구동 노드의 토픽·메시지 타입을 맞춰야 한다.

## 3. AMCL — 저장 지도에서 위치 추정

AMCL은 Adaptive Monte Carlo Localization, 즉 적응형 몬테카를로 위치 추정이다. 알려진 2D 지도에서 `(x, y, θ)`를 추정한다. 여러 위치 가설을 입자로 표현하고 불확실성에 따라 입자 수를 조절한다.

1. **예측:** 오도메트리 이동량과 잡음을 반영해 입자를 이동시킨다.
2. **관측 갱신:** 각 위치 가설에서 지도와 실제 레이저 관측이 얼마나 맞는지 평가한다.
3. **재표본화:** 관측에 잘 맞는 가설이 다음 입자 집합에 많이 남도록 한다.

RViz의 2D Pose Estimate는 초기 위치·방향 가설을 주는 기능이다. 입자가 모였더라도 반복 복도나 잘못된 지도에서는 틀린 위치로 수렴할 수 있다.

### 입력 설정과 주요 파라미터

| 묶음 | 항목 | 확인할 내용 |
| --- | --- | --- |
| 좌표계 | `global_frame_id`, `odom_frame_id`, `base_frame_id` | 실제 TF의 map·odom·로봇 프레임 이름 |
| 입력·모델 | `scan_topic`, `robot_model_type` | 레이저 입력 및 Waffle의 차동 구동 모델 |
| 입자 수 | `min_particles`, `max_particles` | 위치 가설 수와 계산 부담 |
| 레이저 모델 | `laser_model_type`, `sigma_hit`, `z_hit`, `z_rand` | 지도와 관측 오차를 평가하는 방식·폭·가중치 |
| 갱신 | `update_min_d`, `update_min_a` | 필터 갱신을 유발하는 이동 거리·회전량 기준 |
| 계산·재표본화 | `max_beams`, `resample_interval` | 평가 광선 수, 재표본화 간격 |
| TF | `tf_broadcast`, `transform_tolerance` | 전역 보정 변환 발행 여부와 시각 여유 |

이동 잡음 계수는 오도메트리의 불확실성을 모델링한다. `alpha1`은 회전에서 회전, `alpha2`는 이동에서 회전, `alpha3`는 이동에서 이동, `alpha4`는 회전에서 이동으로 전달되는 잡음에 관련된다. `alpha5`는 옴니 구동 모델의 추가 항이다. 수치를 크게 한다고 위치 추정이 항상 좋아지는 것은 아니다.

회전할 때 스캔이 지도 벽에서 벗어나면 먼저 센서 TF·타임스탬프·odom 방향·초기 위치를 확인한다. TF 시간 여유나 입자 수를 키우는 것으로 잘못된 입력을 해결하려 하지 않는다. 파라미터의 정확한 의미는 [AMCL 공식 설정 문서](https://docs.nav2.org/rolling/configuration_and_development/configuration_guide/others/configuring_amcl/)를 설치 버전과 대조한다.

## 4. 전역 경로 계획 — Dijkstra와 A*

### 최소 비용 경로와 기계공학의 경로 최적화

기계공학에서 후보 경로를 비교해 가장 좋은 경로를 찾는 것과 같은 최적화 관점으로 이해할 수 있다. 다만 최소화하는 목적을 구분해야 한다. 이동 거리만 비용으로 두면 최단 거리 문제에 가깝고, 장애물 근접 비용까지 넣으면 조금 길더라도 벽에서 떨어진 경로가 더 낮은 비용을 가질 수 있다.

따라서 **최소 비용 경로는 정한 비용 기준에서 가장 유리한 경로**다. 최단 시간·최소 에너지·최단 거리가 자동으로 모두 같아지는 것은 아니다.

| 알고리즘 | 후보 우선순위 | 의미 |
| --- | --- | --- |
| Dijkstra | 누적 비용 `g` | 지금까지의 비용이 작은 후보부터 확장. 비음수 간선 비용의 그래프에서 최소 비용 경로 탐색 |
| A* | `f = g + h` | 누적 비용에 목표까지 남은 비용의 추정값을 더해 탐색 방향을 유도 |

심리학에서 배운 휴리스틱처럼 판단을 돕는 추정이라는 연결점은 있다. 여기서 `h`는 목표까지의 남은 비용을 추정하는 함수이며 편향 그 자체를 뜻하지 않는다. 적절한 추정은 불필요한 확장을 줄일 수 있지만, A*가 항상 더 빠르거나 더 짧은 경로를 보장하는 것은 아니다. 최적성은 휴리스틱과 탐색 구현의 조건에 달려 있다.

강의의 NavFn에서는 `use_astar`로 Dijkstra/A*를 선택한다. 비교할 때 지도·출발점·목표·비용 설정을 고정한다. Smac 2D·Hybrid-A*·State Lattice·Theta* 등은 로봇의 운동 제약과 경로 요구에 맞춰 추가 검토한다.

## 5. 지역 계획·제어 — DWB와 MPPI

### DWB Controller와 Critic

DWB는 속도 후보를 만들고 짧은 미래 궤적을 예측한 뒤, Critic으로 장애물·경로·목표와의 관계를 평가한다. 유효한 후보 중 가중 비용이 낮은 궤적의 속도 명령을 선택한다.

장애물과 충돌하는 것으로 판정된 궤적은 유효 후보에서 제외될 수 있다. 반면 장애물에 가까워지는 모든 속도 후보가 즉시 탈락하는 것은 아니다. 충돌 여부와 근접 비용은 구분해야 하며, 활성 Critic과 Costmap·Footprint 설정에 따라 평가가 달라진다. [ObstacleFootprintCritic 공식 설명](https://docs.nav2.org/jazzy/configuration_and_development/configuration_guide/controller_plugins/dwb_controller/trajectory_critics/obstacle_footprint/)도 로봇 외곽과 장애물의 접촉 검사를 다룬다.

- 장애물 관련 Critic: 접근 비용·Footprint 충돌 평가.
- 경로 관련 Critic: 경로와의 거리·방향 정렬 평가.
- 목표 관련 Critic: 목표 거리·방향과 마지막 회전 평가.
- Oscillation: 반복적으로 왕복하는 동작 억제.

속도·가속 한계, 예측 시간 `sim_time`, 속도 샘플 수, Critic 가중치를 함께 본다. 후보를 많이 만들면 계산 부담도 증가한다. DWB는 궤적 생성기를 선택하므로 DWA와 완전히 같은 구현으로 단정하지 않는다.

### MPPI Controller

MPPI(Model Predictive Path Integral)는 여러 제어 시퀀스를 샘플링해 미래 궤적을 예측하고, 비용에 따라 제어 시퀀스를 가중 갱신한다. 첫 제어만 적용하고 다음 주기에 새 관측으로 다시 계산한다.

주요 조정 항목은 예측 단계 수 `time_steps`, 단계 시간 `model_dt`, 후보 수 `batch_size`, 속도·가속 한계와 Critic 가중치다. 강의 예시의 `56 × 0.05 s`는 2.8초의 예측 시간이다.

Jetson에서는 계산 부담이 우려된다는 점을 기록하되, 기종·전력 모드·다른 작업·설정에 따른 측정 없이 가동 불가능으로 확정하지 않는다. GPU 필수 알고리즘도 아니다. 설정을 늘리기 전에 한 제어 주기 안에 계산을 마치는지 확인해야 한다. 오늘은 장치별 실행 시간을 측정하지 않았다.

## 6. Costmap과 로봇 외곽

| 항목 | 의미 |
| --- | --- |
| Global Costmap | 보통 `map` 기준으로 전역 경로 계획에 사용 |
| Local Costmap | 보통 `odom` 기준의 Rolling Window로 주변 제어에 사용 |
| Static Layer | 저장 지도 반영 |
| Obstacle / Voxel Layer | 센서 관측으로 장애물 정보 반영 |
| Inflation Layer | 장애물 주변에 비용을 퍼뜨려 거리 확보 유도 |
| `robot_radius` / `footprint` | 원형 반경 또는 다각형으로 표현한 로봇 외곽 |
| `resolution` | **Costmap 셀 하나의 실제 크기(m/cell)** |
| `width` / `height` | Costmap이 다루는 공간의 가로·세로 범위(m) |

Footprint에는 실제 차체와 부착물을 반영한다. 이동량·회전량을 설정하는 항목이 아니다. 해상도를 작게 하면 공간 표현이 세밀해지지만 같은 범위를 표현하는 셀 수가 늘어난다. 예를 들어 같은 면적에서 해상도를 절반으로 줄이면 셀 수는 대략 네 배다.

### Inflation과 센서 장애물 처리

- `inflation_radius`: 장애물 주변에 비용을 퍼뜨리는 범위. 로봇 반경과 구분한다.
- `cost_scaling_factor`: 비용의 거리 감쇠 계수. 같은 반경에서 커질수록 비용이 더 빨리 감소한다.
- `obstacle_max_range`: 장애물 등록에 사용하는 최대 거리.
- `raytrace_max_range`: 광선을 따라 비어 있는 공간을 확인해 장애물을 해제하는 최대 거리.
- `marking` / `clearing`: 장애물 등록·해제 여부.

유령 장애물이 남으면 위 설정과 함께 센서 갱신·시간·TF를 확인한다. 레이어는 설정 블록이 있어도 활성 `plugins` 목록에 포함되어야 사용된다.

## 7. 도착 판정·명령 후처리·계산 주기

`xy_goal_tolerance`는 목표 위치, `yaw_goal_tolerance`는 목표 방향의 허용 오차다. 제어에서 배운 dead band와 비슷하게 허용 범위 안의 오차를 받아들인다는 관점으로 이해할 수 있지만, 목표 성공 판정과 제어기의 불감대는 동일한 기능은 아니다. NavFn의 `tolerance`는 경로 끝점 탐색 범위이므로 구분한다.

Progress Checker는 일정 시간 내 충분히 진행했는지 판단한다. 낮은 속도로 실습하면서 진행 기준을 지나치게 엄격하게 설정하면 정상적인 저속 이동도 실패로 판정할 수 있다.

| 구성 | 역할 |
| --- | --- |
| Velocity Smoother | 속도 명령의 변화와 가감속 제한 조정 |
| Collision Monitor | 센서 기반으로 추가 감속·정지 수행 |
| Behavior Server | 회전·후진·대기 등의 복구 동작 제공 |

Controller와 후처리 노드·구동계의 속도 및 가감속 한계를 맞춘다. `controller_frequency`는 제어 계산 주기, Costmap의 `update_frequency`는 내부 갱신 주기, `publish_frequency`는 전송·표시 주기다. 수치를 높이는 것만으로 성능이 좋아지지는 않는다.

## 8. 현재 실습에서의 조정 순서

현재는 Costmap 범위와 로봇 속도부터 조절해 주행을 이해하는 것을 우선한다. 다만 지도·TF·시간·센서·로봇 외곽 설정이 맞는 것을 전제로 한다.

1. 지도와 센서 정렬, TF, 시간, odom, AMCL 초기 위치를 확인한다.
2. Footprint와 Costmap 범위를 확인하고 속도·가감속 한계를 맞춘다.
3. 필요할 때 Planner → Controller → 도착·진행 판정 순으로 조정한다.
4. 한 항목씩 바꾸고 동일 조건에서 성공 여부·시간·벽과의 간격·진동·계산 시간을 기록한다.

| 증상 | 먼저 볼 항목 |
| --- | --- |
| 벽에 너무 붙음 | Footprint·Inflation, 이후 계획 비용·장애물 Critic |
| 코너에서 진동 | 위치 추정·경로·속도 및 회전 한계·Critic 간 균형 |
| 명령은 있으나 정지 | 명령 타입·토픽, Lifecycle 상태, 충돌 감시 조건 |
| 회전하면 지도와 스캔이 어긋남 | 센서 TF·시간·odom·초기 위치 |

## 9. 질문으로 정리한 내용

### 자율주행에서는 왜 후진을 가급적 자제할까?

후진을 줄이는 경우가 있다는 말을 듣고 그 이유가 궁금했다. 모든 자율주행 시스템이 후진을 금지하는 것은 아니다. 후방 센서의 범위와 사각지대, 전방 주행을 기준으로 설계한 인지·제어, 주변 사람의 동작 예측 가능성 등을 고려해 전진을 선호할 수 있다. 차량에서는 조향과 전후진 전환을 고려한 계획도 필요하다. 주차·도킹·좁은 공간 탈출에는 후진이 필요한 경우가 있다.

따라서 후진 자제의 이유를 회전 오차 최소화 하나로 설명하기는 어렵다. Waffle에서는 후방 장애물 관측 범위와 실제 주행 목적을 확인한 뒤 정책을 정해야 한다. 전진에 낮은 비용을 주는 것, 음의 선속도를 금지하는 것, 복구 동작의 후진을 허용하는 것은 서로 다른 설정이다. 오늘 기록에서는 특정 실습에서 후진을 제한한 실제 이유까지 확인하지 못했다.

### AMCL과 SLAM을 동시에 실행하면 위치 추정이 더 좋아질까?

두 방법을 함께 사용하면 더 좋은 추정을 얻을 수 있을 것 같아, 서로 다른 임베디드에서 계산하고 통신하는 구성을 생각했다. 계산을 분산하는 것은 가능하지만, 추정 결과를 어떻게 사용하느냐를 정해야 한다.

저장 지도 주행에서는 보통 AMCL이 `map → odom`을 발행하고, SLAM 주행에서는 SLAM 노드가 이 보정을 담당한다. 두 노드가 같은 좌표계 쌍에 서로 다른 변환을 발행하면, 하나의 일관된 전역 위치를 보장할 수 없다. 지도 위 로봇 위치나 스캔 정렬이 흔들리고 경로 추종에 영향을 줄 수 있다. 장치를 나누어도 같은 TF 관계를 함께 발행하면 이 문제는 남는다.

하나의 센서 토픽을 두 노드가 구독하는 것은 가능하다. 문제는 센서 공유가 아니라 **서로 다른 두 추정값을 하나의 위치로 어떻게 결정할지**다. 토픽 이름만 바꾸어도 TF의 부모·자식 프레임이 같으면 충분한 분리가 아니다.

| 구성 | 고려할 점 |
| --- | --- |
| SLAM으로 지도 작성 후 AMCL 주행 | 단계별로 전역 TF 발행 주체를 전환하는 기본 구성 |
| 두 추정기를 동시에 비교 | 별도 결과로 관찰하고 주행용 전역 TF 발행 주체는 하나로 지정 |
| 두 임베디드에서 분산 계산 | 지도·좌표계·시각·통신 지연을 맞추고 결과 선택·융합 방법 설계 |

AMCL의 `tf_broadcast: false`는 AMCL의 전역 TF 발행을 막는 설정이다. 이를 끈다고 SLAM과 AMCL의 추정이 자동으로 융합되는 것은 아니다. 두 추정기가 같은 센서·오도메트리를 사용하면 오차가 서로 연관될 수 있어 단순 평균도 개선을 보장하지 않는다. 동시 실행과 센서 융합은 별개의 설계 문제다. [Nav2 공식 TF 구조 설명](https://github.com/ros-navigation/docs.nav2.org/blob/rolling/docs/configuration_and_development/first_time_robot_setup_guide/transformation/setup_transforms.md)을 함께 참고한다.

오늘의 핵심은 알고리즘 수를 늘리기 전에 지도·좌표계·시간을 일치시키고, 위치 추정·계획·제어 각 단계의 역할과 출력 책임을 명확히 하는 것이다.
