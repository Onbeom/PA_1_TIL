# 37강 SLAM 원리와 도구 비교

## SLAM이 필요한 이유
- 오도메트리: 바퀴 엔코더 회전을 적분해 위치 추정
  - 연속적이지만 바퀴 미끄러짐·지름 오차가 적분되어 누적(드리프트)
  - 한 바퀴 돌아 출발점에 와도 추정 위치는 어긋남
- 로봇 이동의 누적 오차를 지도와 방의 모양을 비교해 보정하기 위해 맵핑
- 위치를 알아야 지도를 그리고, 지도가 있어야 위치를 앎 → 둘을 동시에 추정하는 것이 SLAM

## 스캔 매칭
- 새 스캔을 조금씩 이동·회전시키며 지도와 가장 잘 겹치는 자세 $(x, y, \theta)$ 탐색
- 오도메트리 추정값을 탐색 시작점으로 사용 → 지도 전체가 아닌 근처만 탐색
- 매칭으로 찾은 자세로 오도메트리 오차 보정

### EKF로 보정값 합치기
- 예측: 오도메트리로 다음 위치 예측 → 불확실성 증가
- 보정: 스캔 매칭 결과를 관측값으로 넣어 위치 갱신 → 불확실성 감소
- 두 값의 불확실성(공분산)을 비교해 더 믿을 만한 쪽에 가중치
- 회전이 들어간 운동은 비선형 → 선형화해서 쓰는 것이 EKF
- Cartographer·slam_toolbox는 필터 대신 그래프 최적화로 합침 (38강에서 비교)

### 공통 구조물이 필요한 이유
- 스캔 매칭 = 스캔과 지도의 겹침 점수가 가장 높은 자세 찾기
- 겹치는 구조물이 없으면 어느 자세에 놓아도 점수가 같음 → 자세를 하나로 못 정함 → 보정 불가
- 꼭 벽일 필요는 없음. 모서리·기둥·장애물 등 지도에 이미 있는 구조면 기준이 됨
- 긴 복도: 복도 방향으로 밀어도 점수가 같음 → 그 방향만 보정 불가

### 이동량이 스캔 주기보다 클 때
- 스캔 사이 이동이 크면 이전 지도와 겹치는 구조가 줄어 매칭 불가 또는 값 신뢰 불가
- 오도메트리 초기값이 탐색 범위 밖으로 벗어날 수도 있음
- 회전이 빠르면 한 스캔 안에서도 형상이 왜곡됨
- 대응: 스캔 주기에 맞게 속도(특히 각속도) 제한
- Cartographer는 직전 스캔이 아니라 누적된 submap에 맞추므로 겹칠 구조가 더 많음

## map·odom·base 프레임
- TF 체인: map → odom → base_footprint → base_link
- map: 전체 지도 기준. SLAM이 보정하면 위치가 바뀔(점프할) 수 있음
- odom: 연속적인 이동 추정. 튀지 않지만 장기 오차 누적
- SLAM은 map → odom 변환을 발행해 odom의 누적 오차를 상쇄
- base_footprint: 바닥 기준 / base_link: 본체 기준

## Loop closure
- 순차 매칭만으로는 작은 오차가 계속 쌓임
- 이전에 본 장소 후보 탐색 → 기하학적으로 같은 장소인지 검증 → 제약 추가 → 전체 경로 최적화
- 제약 하나가 그동안 쌓인 드리프트를 경로 전체에 나눠 교정
- 비슷한 복도를 같은 곳으로 착각하면 지도가 찌그러짐 → 검증 단계가 필요한 이유

## Cartographer
- Local SLAM: 짧은 구간의 스캔을 겹쳐 submap 생성, 현재 스캔을 활성 submap에 맞추며 이동 추정
- Global SLAM: 완성된 submap 사이 제약(loop closure 포함)을 최적화해 전역 오차 최소화
- 2D·3D 모두 지원, 수업 예제는 2D

### use_sim_time을 켜야 하는 이유
- Isaac Sim은 `/clock`으로 시뮬레이션 시간 발행, 센서 메시지 stamp도 시뮬레이션 시간 기준
- 시뮬레이션 속도는 GPU 부하에 따라 실제보다 느리거나 빠르고, 일시정지·리셋도 있음 → 시스템 시간과 맞출 수 없음
- 일부 노드만 시스템 시간을 쓰면 TF 조회 시각과 메시지 시각 불일치
  - `TF extrapolation` 에러, 메시지 버림, 지도 멈춤
- 모든 노드에 `use_sim_time:=true`로 시간 기준 통일 (rosbag 재생 시에도 `--clock`)
- 실제 로봇은 시스템 시간 사용

## 3D 지도를 많이 안 쓰는 이유
- 실내 지상 로봇은 평평한 바닥에서 $(x, y, \theta)$로만 움직임 → 2D 지도로 충분
- 3D는 메모리·계산량 증가, 3D LiDAR는 2D LiDAR보다 훨씬 비쌈
- 높이가 중요한 곳은 3D 사용: 드론, 매니퓰레이터, 사족보행(높이 지도), 울퉁불퉁한 실외 지형

### 2.5D 지도 (높이 지도)
- 2D 격자의 칸마다 높이 값 하나 저장 → 데이터량은 2D 격자와 비슷 (`grid_map`, `elevation_mapping`)
- 부호로 구덩이(음수)·턱(양수) 표현 가능
- depth 이미지처럼 색으로 보이는 것은 시각화일 뿐, 저장하는 것은 숫자 값
- 한계: 칸마다 높이가 하나 → 아래가 빈 구조(책상 밑, 선반, 다리 밑, 복층) 표현 불가
  - 책상 상판만 기록되어 그 밑을 지나갈 수 없는 칸이 됨
- 진짜 3D 지도는 복셀 사용 (OctoMap, nvblox의 TSDF), 빈 공간은 저장하지 않는 구조로 용량 절약
- 2D 지도에 z만 추가한다고 3D SLAM이 되지는 않음 → 자세 추정도 roll·pitch·z까지 포함한 6DoF여야 함

### 자동차
- 위치 추정은 3D: 3D LiDAR로 미리 만든 점군 지도에 현재 스캔을 정합 (Autoware의 NDT 매칭) → 3D 스캔 매칭
- 경로 계획은 2D: 도로면 위 차선 지도에서 계획
- 3D로 측정·위치 추정, 계획은 2D로 내림 → nvblox의 2D 슬라이스와 같은 발상
- 예외: Tesla처럼 HD 지도 없이 카메라로 주변 3D 점유를 실시간 추정하는 방식
  - 넓은 도로망의 HD 지도를 계속 최신으로 유지하는 비용이 크기 때문
