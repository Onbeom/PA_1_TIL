## 2. 전체 구조: 계획 · 제어 · 학습
- 계획기(planner): 경로·궤적을 만듦
- 제어기(controller): 실제 상태를 읽으며 구동기에 명령
- 정책(policy): 관측을 보고 행동을 고름
- 흐름: 카메라·관절 피드백 → 인식·좌표변환(물체 자세, TF) → 계획 또는 정책(목표·궤적) → 구동기
  - 시간·좌표계·관절 이름을 모든 단계에서 일치시켜야 함
  - YOLO의 2D 상자를 바로 팔의 3D 목표로 쓰지 않음 → 자세 추정·깊이·TF·관절 피드백의 시각과 좌표를 맞춘 뒤 사용
- **계획 궤적 추종과 정책 추론은 다른 실행 모드**
  - 같은 관절에 두 노드가 동시에 명령하면 안 됨 → 명령 모드 선택기(selector)를 둠

## 3. 로봇 기술 파일: URDF · SRDF · XRDF · USD
| 파일 | 맡는 것 | 쓰는 곳 |
|---|---|---|
| URDF | 링크·관절·질량·형상 (기구) | ROS 전체, 변환의 출발점 |
| SRDF | 계획 그룹, 엔드 이펙터, 충돌 제외 쌍 | MoveIt |
| XRDF | 충돌 구(sphere), cuMotion용 로봇 구성 | cuMotion(cuRobo 기반 GPU 계획기) |

- 모양 하나로 계획·학습·실기 설정이 다 끝나지 않음 → 파일마다 따로 채워야 함
- **관절 이름과 TCP(도구 기준점)는 네 파일 모두에서 같아야 함**
- Waffle 4WD에서는 URDF → SRDF(MoveIt 충돌 확인) → USD까지 만듦: [261021 5장](../261021/ROS2.md#5-moveit-2-충돌-확인-5개-모두-성공), [6장](../261021/ROS2.md#6-2단계-일부-isaac-sim-usd-생성-usd-생성-성공-importer-오류-0). XRDF는 아직 없음

## 4. 기구학
### 순기구학 (FK)
- 관절값 $q$ → TCP의 위치·자세
- $T_{\text{base,TCP}}(q) = T_1(q_1)\,T_2(q_2)\cdots T_n(q_n)$
  - $T_i$: $i$번째 관절(과 링크)의 4×4 동차 변환 행렬. 앞에서부터 차례로 곱함
- 확인법: 관절 하나씩 양(+)의 방향으로 움직여서 URDF의 축 방향·원점이 맞는지 봄

### 역기구학 (IK)
- 목표 TCP → 그 자세를 만드는 관절값
- 해가 여러 개일 수 있음 (팔꿈치 위/아래 등), 작업 공간 밖이면 해가 없음
- 해를 고를 때: 관절 한계, 충돌, 현재 자세와의 거리
- 자유도가 부족한 팔에 임의의 6D 자세(위치 3 + 방향 3)를 요구하지 않음
  - Waffle 4WD 팔은 5자유도라 `position_only_ik: true`로 둔 것과 같은 이야기 → [261021 5장](../261021/ROS2.md#5-moveit-2-충돌-확인-5개-모두-성공)
- 보충: 수치 IK는 야코비안으로 반복 계산
  - $\dot{x} = J(q)\,\dot{q}$ (관절 속도 → TCP 속도)
  - 갱신 예(감쇠 최소제곱): $\Delta q = J^{\top}(J J^{\top} + \lambda^2 I)^{-1} e$, $e$ = 목표 − 현재 TCP 오차
  - $\lambda$는 특이 자세 근처에서 $\Delta q$가 폭주하지 않게 막는 감쇠 값

## 5. MoveIt Setup Assistant (교안의 공식 화면, 예제 로봇은 Panda)
- 실습은 Panda가 아니라 자기 로봇으로 진행
- 순서별로 볼 것
  - URDF 불러오기: 링크가 실제 크기·방향으로 보이는지 (mesh = 표면 형상, collision = 충돌용 형상)
  - 계획 그룹(planning group): `arm`에 넣을 관절 체인 선택. **집게 관절을 팔 체인에 섞지 않음**
  - 엔드 이펙터: 손목 링크와 물체를 잡는 기준점(TCP)은 다를 수 있음 → 목표 좌표가 어느 링크에 걸리는지 확인
  - 자기충돌 제외 목록(collision matrix): 자동 결과를 그대로 믿지 말고 실제 관절 범위에서 확인, 제외 이유 기록
- Waffle 4WD에서 이미 겪은 일: 샘플 0개로도 "Never" 49쌍을 제외하자는 제안이 나와서 인접 13쌍만 받음 → [261021 5장](../261021/ROS2.md#5-moveit-2-충돌-확인-5개-모두-성공)

## 6. 충돌 검사와 cuMotion
### 충돌 검사
- 관절 공간에서 보면 "충돌하는 관절 조합" 영역을 피해 시작 → 목표로 가는 경로를 찾는 문제
- 검사 대상: 팔 + 집게 + **잡은 물체**
- 충돌 쌍을 다 제외하면 경로는 쉽게 나오지만 실제로는 통과할 수 없는 경로가 됨
- XRDF 충돌 구
  - 너무 작음 → 충돌을 놓침 / 너무 큼 → 지나갈 수 있는 통로를 막음
  - 구가 링크와 집게를 빈틈없이, 과하지 않게 덮는지 확인

### cuMotion
- GPU로 로봇 모델·목표·주변 장애물을 함께 고려한 궤적(시간 정보가 있는 경로)을 계산
- 필요한 것: MoveIt 플러그인 + cuMotion 서버 + 내 URDF/XRDF
- 실제 모터 통신은 cuMotion이 아니라 ros2_control이나 별도 드라이버가 담당
- 교안 시연 영상에서 볼 점
  - 목표가 바뀌면 경로가 어떻게 달라지는지
  - 장애물이 움직이면 언제 다시 계획(replanning)하는지, 장애물 속도와 반응 지연
  - 계획 계산 시간 ≠ 전체 시스템 지연 (궤적 추종·통신 포함)

| | cuMotion | cuRobo (V2) |
|---|---|---|
| 성격 | ROS(MoveIt)에 통합된 계획기 | GPU 운동 생성 연구 도구 |
| 언제 | 기본 실습 (Lyrical의 cuMotion 플러그인 경로) | 최적화 비용·동역학을 직접 연구할 때 비교 |

- 공통점은 GPU 계획이지만 구현은 구분해서 말함

### nvblox와 잡은 물체
- 깊이 영상 + TF로 주변 형상 지도를 갱신 → 계획기의 장애물로 사용
- 정할 것: 로봇 자신을 지도에서 빼는 방법, 잡은 물체를 어떻게 처리할지
- 순서: 카메라 보정·TF·시간 맞추기 → 그다음 ESDF(장애물까지의 부호 있는 거리장) 연결
- 초기 cuMotion 실습은 ESDF 서비스가 없으므로 `read_esdf_world=false`

## 7. 제어: ros2_control · Servo · 힘 제어
### ros2_control
- controller → hardware interface → 모터·센서
  - command interface: 목표를 씀 (position / velocity / effort 중 **구동기가 실제로 지원하는 것**)
  - state interface: 관절 상태를 읽음
- 명령값을 측정값인 것처럼 되돌려 보내지 않음 (가짜 피드백이면 추종 실패를 못 봄)
- 컨트롤러 이름·관절 목록·MoveIt Action 경로를 서로 맞춤
- **계획 성공과 실행 성공은 따로 확인**
- Waffle 4WD MoveIt 설정은 아직 컨트롤러 없이 충돌 확인만 한 상태 ([261021 5장](../261021/ROS2.md#5-moveit-2-충돌-확인-5개-모두-성공))
- Isaac 쪽 관절 드라이브의 PD 추종 식 $\tau = k_p(q_\text{목표} - q) + k_d(\dot q_\text{목표} - \dot q)$은 [261021 6장](../261021/ROS2.md#6-2단계-일부-isaac-sim-usd-생성-usd-생성-성공-importer-오류-0)에 정리

### MoveIt Servo
- (목표 − 현재) 오차를 보고 짧은 주기로 반복 보정 → 새 상태를 읽고 다음 명령 계산
- 장애물을 크게 돌아가는 계획을 대신하지 않음
  - 전역 이동 = 계획기, 마지막 위치 보정 = Servo로 나눠서 비교
- 보충: Servo는 TCP 속도 명령(Twist: 선속도·각속도)을 야코비안 역(유사역행렬)으로 관절 속도로 바꿔 보냄

### 접촉 작업의 힘 제어
| | 임피던스 | 어드미턴스 |
|---|---|---|
| 설계하는 관계 | 위치 오차 → 힘 | 측정된 힘 → 운동 |
| 보충: 대표 식 | $F = K(x_d - x) + D(\dot x_d - \dot x)$ | $M\ddot{e} + D\dot{e} + K e = F_\text{ext}$, $e = x - x_d$ |
| 보충: 잘 맞는 구동기 | 토크(전류) 제어가 되는 관절 | 위치 제어 위주의 관절 + F/T 센서 |

- 모터 전류만으로 손목의 외력을 정확히 안다고 가정하지 않음 (감속기 마찰 등)
- 먼저 센서·구동기 기능·갱신 주기·안정성을 확인

## 8. 작업 구조: 접근 → 집기 → 놓기
- 목표 자세 하나로 집기 작업 전체를 설명할 수 없음 → 단계마다 조건과 동작이 다름
- 단계별 확인
  - 접근 전 장애물 확인 → 집게 닫힘 확인 → 들고 옮기는 동안 물체 유지 확인 → 놓은 뒤 손 떼기
- 실패하면 재탐색 / 재접근 / 종료 중 어디로 갈지 미리 정함 → 상태 머신(state machine)
- MTC(MoveIt Task Constructor)가 이런 단계 구성을 다루는 도구

## 9. 정책학습 (Isaac Lab)
- RL 기본 용어·PPO 식은 [261019 강화학습](../261019/ROS2.md#강화학습), [261019 PPO](../261019/ROS2.md#ppo)에 정리. 여기서는 로봇팔에 붙일 때 달라지는 점만
- 정책 $a_t \sim \pi_\theta(a \mid o_t)$
  - 학습 = 가중치 $\theta$를 바꿈 / 추론 = 고정된 가중치로 실행
  - 관절 목표와 모터 토크는 서로 다른 행동 → 단위·범위·주기를 먼저 정의
- 목표는 한 스텝 보상이 아니라 에피소드 전체의 누적 성과
- 환경 = 로봇 모델 + 센서 + 행동 + 보상 + 종료 조건

### PPO · RSL-RL · Actor-Critic
- PPO = 정책을 갱신하는 **알고리즘**, RSL-RL = 학습을 돌리는 **라이브러리**
- rollout(수집한 경험)을 모은 뒤 actor와 critic을 학습
- 클립 목표 $L^{CLIP} = \mathbb{E}_t\left[\min\left(r_t \hat{A}_t,\ \text{clip}(r_t, 1-\epsilon, 1+\epsilon)\hat{A}_t\right)\right]$, $r_t = \dfrac{\pi_\theta(a_t \mid o_t)}{\pi_\text{old}(a_t \mid o_t)}$
  - $\hat{A}_t > 0$이면 $r_t$가 $1+\epsilon$을 넘는 순간부터 이득이 더 늘지 않음 → 한 번에 크게 바뀌지 않음
  - 보상이 늘어도 실제 성공률은 따로 확인
- Actor: 관측 → 행동 / Critic: 관측 → 앞으로 얻을 성과(가치 $V$) 추정
  - 시뮬레이터만 아는 정답(참값)은 **Critic에만** 넣을 수 있음
  - 배포할 Actor의 입력은 실기에서 얻을 수 있는 값이어야 함 → [261021 정책 관측과 진단 정보 분리](../261021/ROS2.md#정책-관측과-진단-정보를-분리)
  - 보충: 이렇게 Actor·Critic 입력을 다르게 두는 방식을 asymmetric actor-critic이라 부름
- 수치 예(clip 0.2 등)는 [261020 PPO 설정](../261020/ROS2.md#ppo-설정-rsl_rl-onpolicyrunner)

### 관측 · 행동 · 보상 · 리셋
| 항목 | 넣을 것 / 정할 것 | 주의 |
|---|---|---|
| 관측 | 관절 위치·속도, TCP 오차, 집게 상태, 이전 행동 | 배열 이름·순서·단위·좌표계 문서화 |
| 행동 | 출력의 의미: 관절 위치 / 증분 / 속도 / 토크 중 하나 | 기준값이 무엇인지 명시 |
| 보상 | 목표 접근, 동작 변화 비용, 충돌 비용, 작업 성공 | 성공 판정을 별도 항으로 |
| 리셋·종료 | 초기조건 샘플 / 성공·실패·시간 종료 | 실패 종료와 시간 종료 구분 |

- 관측: 카메라로 본 물체 자세를 world 기준으로 학습했다면 실기에서도 같은 기준으로 변환해서 넣음
- 행동 변환
  - $q_\text{target} = \text{clip}(q_\text{ref} + s \cdot a,\ q_\text{min},\ q_\text{max})$
  - $q_\text{ref}$가 **현재 관절값인지 고정 기준(기본 자세)인지** 반드시 적어 둠 → 같은 $a$라도 의미가 완전히 달라짐
- 보상
  - $r = -w_d\,d - w_a\lVert \Delta a \rVert^2 - w_c\,c + w_s\,s$
  - $d$: 목표까지 거리, $\Delta a$: 직전 대비 행동 변화(급격한 동작 억제), $c$: 충돌, $s$: 성공
  - 거리만 줄이고 물체를 놓치는 편법을 막으려고 실제 작업 성공 판정을 따로 둠 (편법 이야기는 [261020 실습 3](../261020/ROS2.md#5-실습-3--보상-계산)과 같은 맥락)
- 리셋과 종료는 따로 설계
  - 리셋: 다음 시도의 초기조건 (물체가 겹치거나 도달 불가능한 곳에 생기지 않게)
  - 종료: terminated(낙하·충돌 등 상태 때문) vs truncated(시간 제한)
  - 보충: truncated는 "실패"가 아니라 중간에 잘린 것이라, 가치 추정에서 다음 상태 가치를 이어서(bootstrap) 계산하는 것이 일반적

### 내 로봇 Task 만들기와 실행 순서
- 공식 생성기로 프로젝트를 만든 뒤 채울 것: `robot_cfg` / `env_cfg` / `observations` / `rewards` / `terminations`
  - 입력: USD + 구동기 설정 → 관측·행동·보상 → Task 등록
  - 관절 수를 6개로 고정하지 말고 실제 관절 이름과 제어 가능한 자유도를 사용
- 구성 방식(Manager/Direct), 병렬 환경 shape, decimation은 [261021 태스크 명세](../261021/ROS2.md#태스크-명세)
- 실행 순서: 무행동(zero agent) → 작은 임의 행동 → 짧은 PPO 학습 → checkpoint 재생 → 병렬 규모 확대
  - 처음부터 수천 개 환경을 켜면 문제 원인이 가려짐
- Lab 3.0 EA는 통합 `isaaclab train/play` 명령 사용, 물리 백엔드를 명시 (`physics=isaacsim_physx`)

## 10. 평가와 Sim-to-Real
- 학습 보상만 보지 않음 → 학습에 안 쓴 초기조건(holdout)에서 성공률과 실패 유형 측정
- 기록 항목: 성공 횟수/총 시도, 위치 오차, 충돌, 완료 시간, 추론 지연
- 계획기 · PPO · 모방학습을 같은 목표·같은 초기조건으로 비교 (교안의 비교표는 모든 칸이 "실측"으로 비어 있음)

| 방법 | 성공률 | 충돌 수 | 시간·지연 |
|---|---|---|---|
| MoveIt / cuMotion | 실측 | 실측 | 실측 |
| PPO 정책 | 실측 | 실측 | 실측 |
| 모방학습 정책 | 실측 | 실측 | 실측 |

- 현실로 옮기기: 질량·마찰·지연·센서 잡음이 다름
  - 먼저 단일 관절·접촉 응답으로 모델을 맞춤 (보정)
  - 그다음 측정한 현실적인 범위에서 변동시킴 (도메인 랜덤화) → [261021 도메인 랜덤화](../261021/ROS2.md#도메인-랜덤화)
  - 실제 실패 원인과 비교

## 11. 모방학습과 VLA
### 모방학습
- 시연의 (관측, 행동)을 정답 쌍으로 학습. 기본은 [261019 모방학습](../261019/ROS2.md#모방학습)
- 정할 것: 실패 구간·복구 시연을 넣을지 뺄지
- 카메라 프레임과 명령의 시각을 맞춤
- train/validation/test는 **에피소드·촬영 세션 단위로** 나눔 (프레임 단위로 섞으면 비슷한 장면이 양쪽에 들어가 성능이 부풀려짐)
- Isaac Lab Mimic: 사람이 원격 조작(teleoperation)으로 모은 시연을 다른 물체 배치로 옮겨 데이터를 늘림
  - 물체 기준 좌표로 동작을 옮김, 작업을 subtask(접근·집기 등)로 나눔
  - 옮긴 궤적이 충돌·실패하면 성공 데이터에서 제외
  - subtask 사이 보간 횟수 → 충돌·시간·움직임 연속성에 영향
  - 자기 URDF만 넣는다고 끝나지 않음: 작업 구간·물체 프레임·성공 조건을 직접 정의
  - 교안 시연: Mimic 데이터로 학습한 BC-RNN(순환 신경망 행동 복제) 쌓기

| 방법 | 핵심 |
|---|---|
| BC (행동 복제) | 시연 행동을 그대로 맞추도록 학습 |
| ACT | Transformer로 행동 묶음(chunk)을 한 번에 예측 |
| Diffusion Policy | 잡음에서 시작해 반복 잡음 제거로 행동 시퀀스를 복원 |

- ACT와 Diffusion은 설치 옵션만 다른 같은 알고리즘이 아님
- 비교할 땐 같은 데이터에서 입력·출력·주기·평가를 맞춤
- Diffusion Policy
  - 학습: 정답 행동에 넣은 잡음을 예측하도록 학습
  - 보충: 손실 형태 $\lVert \epsilon - \epsilon_\theta(a^k, k, o) \rVert^2$ ($a^k$: $k$단계 잡음이 섞인 행동, $o$: 관측)
  - 실행: 여러 단계 추론 → 지연과 행동 실행 길이를 함께 측정
  - 미래 동작을 길게 실행할수록 최신 관측 반영이 늦어짐

### VLA (GR00T)
- 영상·언어·로봇 상태 → 행동. 서로 다른 로봇(embodiment)의 관측·행동을 연결하려는 접근
- 새 로봇에 쓰려면 센서·행동 설정과 **자체 데이터**가 필요
- 내 로봇 데이터: 영상·관절 상태·행동·언어 지시를 같은 시각 기준으로 저장 → modality 설정 → 미세조정 → 폐루프 평가
  - 맞출 것: modality key, 단위, 상대/절대 행동, 집게 범위, 주기
  - GR00T는 별도 venv에 고정 revision으로 설치
- VLA + 강화학습(RLinf 예제)은 확장 연구
  - 기본 PPO와 설치·학습 비용이 다름. 예제의 GR00T·transformers 고정 버전을 따로 유지
  - 최신 N1.7 환경에 N1.5 기반 예제를 합치지 않음
- VLA 개념은 [261019 VLA](../261019/ROS2.md#vla)

## 12. 배포와 문제 진단
- 배포 구조: 관측 어댑터 → 정책·제한·선택 → 구동기 드라이버
  - 상태가 오래되었거나(watchdog) NaN이면 유지 또는 정지로 전환
  - 계획기·Servo·학습 정책 중 **하나만** 제어권을 가짐
- 진단 순서: 모델 형상 → 한 관절 → 상태 수신 → 작은 명령 → 계획 → 학습
  - 여러 개를 한꺼번에 바꾸면 원인을 못 찾음
  - 학습 전 단계에서 실패한 걸 더 긴 학습으로 해결하려 하지 않음
- ROS 브리지 통과 순서: `/clock` → `/joint_states` → TF → 작은 명령 → Action 결과
  - 같은 네트워크에 있다는 것만으로 통신 검증이 끝나지 않음 (QoS·RMW 설정도 맞아야 함)
- 완료 기준: 다른 사람이 재현하고 성공·실패 원인을 확인할 수 있어야 함
  - 제출물: URDF/USD/SRDF/XRDF, 제어·학습 코드, 버전 기록, checkpoint, 평가표, 실행 영상
  - 실기 미검증 항목은 미검증으로 그대로 표시

## 핵심 용어
| 용어 | 뜻 |
|---|---|
| TCP | 도구 기준점 (목표 좌표가 걸리는 점) |
| planning group | 함께 계획할 관절 집합 |
| collision matrix | 링크 쌍별 충돌 검사 여부 |
| XRDF | cuMotion용 로봇 구성 (충돌 구 포함) |
| ESDF | 장애물까지의 부호 있는 거리장 |
| command / state interface | ros2_control에서 명령을 쓰는 / 상태를 읽는 통로 |
| rollout | 정책으로 수집한 경험 |
| terminated / truncated | 상태 때문에 끝남 / 시간 등 제한으로 잘림 |
| holdout | 학습에 쓰지 않은 평가 조건 |
| embodiment | 로봇의 몸체·센서·구동 구조 |
